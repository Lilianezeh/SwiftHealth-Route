## Phase 1: one password rule (FR-56, NFR-06)

- **Rule (owner, 2026-10-24):** a provider's password: **8 to 128 characters**; a verifier, editor or admin password: **10 to 128**; for everyone: not on the common-password list (compared in lower case) and not equal to the email. **Nothing is weakened for staff and admin.**
- **Files:** `backend/app/core/passwords.py` (new: `min_length_for(role)`, `check_password(password, role, email)` raising `PasswordRuleError`, a `ValueError`), `backend/app/core/common_passwords.txt` (new, plain text, source and licence at the top, only entries of 8 characters or more because shorter ones fail the length rule anyway), `schemas/admin_user.py` (the fixed `min_length` goes; a validator calls `check_password` with the account's role), `services/admin_user_service.py` (a password sent without a role in `PATCH` is checked against the stored role; a role change from provider to a staff role needs a new password in the same request, so a short provider password never becomes a staff password), `routes/admin.py` (translates the domain error to 422), `bootstrap_admin.py` (the same function with `Role.admin`; the message names the variable, never the value), frontend `StaffAccounts.tsx` (the hint and the check follow the chosen role: 8 or 10), `specs/backend/api-spec.md` section 11, `specs/frontend/ui-spec.md` 3.8, `specs/prd.md` (the new IDs FR-48 to FR-56 and US-17 to US-21).
- **Tests first:** provider: 7 refused, 8 accepted; staff and admin: 9 refused, 10 accepted; 129 refused for all; a sample of listed passwords refused for every role in upper, lower and mixed case; the email as a password refused; `POST /admin/users` and `PATCH` (with a role, and with the stored role) use the same function; provider to editor without a new password is refused, with a 10-character one accepted; bootstrap with a 9-character password still fails and with a listed one fails naming only the variable; the log and the error never contain the password; a test finds no second length constant in the backend; frontend: the hint and the message change with the role.

## Phase 5: account self-service (FR-54, US-21)

- **API (logged-in user, own account only; the id never comes from the request):** `GET/PATCH /account` (name; a new phone or email goes through a code sent to the **new** address and replaces the old only after it is confirmed; the old email gets a notice), `POST /account/password` (current password and new one; sets `password_changed_at`), `POST /auth/forgot-password` (always the same answer) and `POST /auth/reset-password` (email, code, new password), `POST /account/close` (password and a typed confirmation). ## Safe migration of existing listings (summary)

1. Every migration is **additive**: new nullable columns, new defaults, one new table; no column dropped, retyped or made `NOT NULL` without a default; no enum value added; downgrades remove only what the same revision added.
2. **Existing users:** approved and confirmed by default; the production admin keeps working (tested).
3. **Existing listings:** untouched (`parent_id` and `closed_at` null); every `owner_id` copied once into `facility_owners` (idempotent) and kept in place; a test counts both sides.
4. **Anonymous drafts** from the old form stay as unowned drafts.
5. Each migration has a test that starts from the previous revision with data of every kind, upgrades, checks the data, downgrades, and upgrades again.
6. Before each production deploy: the PR says the revision id, the owner confirms the latest backup (NFR-09), and the Dockerfile's `alembic upgrade head` runs it.
