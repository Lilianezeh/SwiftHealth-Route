## Phase 3a: sign-up API (FR-48, FR-49, FR-56; draft PR, 2026-10-25)

**What changed for people (nothing visible yet: no page, and closed in production):** `POST /auth/signup`, `/auth/confirm-email`, `/auth/confirm-phone` and `/auth/signup-resend-code` (api-spec 4c). A provider signs up, confirms an email code and an SMS code and can then log in; a staff sign-up does the same and then waits for an admin (`pending`, refused by every route that needs a login), and the admins get an email with the name only. The answer is the same for an email that is already an account (the owner gets a notice, nobody can tell who has an account). **The password is the shared rule: 8 for a provider, 10 for staff, nothing common.** A nightly clean-up deletes sign-ups never confirmed within 7 days that no other row names.

**What changes on Render (for the owner):** **nothing happens until you decide.** No migration (the columns exist since Phase 2), no package. **`SIGNUP_ENABLED` is not set, so every sign-up route answers 503 "Sign-up is not open yet."** To open sign-up later you set `SIGNUP_ENABLED=true` **and** Resend (`RESEND_API_KEY`, `RESEND_FROM_EMAIL`, a verified sending domain) **and** Termii (`TERMII_API_KEY` and the rest, live account, DND route, approved sender ID) must already be set: with any of these missing sign-up stays closed, so no account is made that nobody can confirm. The Privacy page review (Phase 9) comes before you open it. The nightly clean-up `python -m app.jobs.purge_signups` has no schedule (like the re-check job); until sign-up is open there is nothing for it to delete.

- **Tests written first:** `tests/integration/test_signup.py` (49 tests) and `tests/integration/test_purge_signups.py` (7). Open or closed (the setting; outside development Resend and Termii; the same closed answer for an existing email); the whole road for a provider (the login is refused until both codes, then works) and for staff (waiting, refused by **every** route of the Phase 2 list, admins emailed with the name only); the password rule per type with its plain sentence; bad input; an email that is already an account (same answer shape, no code, a notice, the account unchanged, the decoy token fails like a wrong code, asking again looks the same and sends nothing); an unfinished sign-up started again; wrong, expired, used and other-purpose tokens; the lock after 10 wrong codes; an SMS that cannot be sent (the email step is not used up) and an email that cannot be sent (nothing is made, 502, or 503 when Resend is not set up); new codes (60 seconds, 5 an hour, for the email and the phone); the 3 per email and 10 per address limits (an existing email counts too); the audit entry has no secret; nothing secret in a log or an answer; the clean-up (older than 7 days, email only confirmed, never a confirmed account or a waiting staff account, never an account another row names, a second run finds nothing, one printed line).
- **Backend: 1726 passed, `ruff` clean** (full run). **Frontend: untouched** (110 files, 1648 tests; three of them failed once under load in the full run, `BloodPages`, `ListingPage` and `TwoFactorSetup`, and passed alone, 89 of 89; `tsc` and `next lint` clean). No Phase 3a code builds a password field; Phase 3b must use the shared `PasswordField`.
- **A thing the work found:** `/auth/resend-code` already exists since Phase 2b for the login code, so the sign-up one is `/auth/signup-resend-code`. The resend route must also answer an existing account's decoy token like a new one, or asking again would reveal it (a test checks).
- **Known limits:** the limits and the lock are in the API's memory (per instance, forgotten at a restart); a token of an old code still works until it expires (nothing is stored); the existing-account notice email needs Resend (without it the owner is not told, and the answer on screen is still the same).

## Phase 2b: the login code screen (FR-57; draft PR, 2026-10-24)

**What changed for people:** the code screen says "Code sent to ••• ••• 4567" (only the last four digits). "Send a new code" is off for 60 seconds after each send, with the seconds counting down in words, and it no longer sends the password again (it uses the current code token: new route `POST /auth/resend-code`). "Start again" goes back to the email and password step with the email kept. The server enforces the same two limits (60 seconds between sends, 5 codes per account per hour, the first one and every new login counted), so a script cannot get around the screen. **Render: nothing changes** (no variable, no package, no migration, no setting).

- **Backend tests (written first):** `tests/integration/test_login_resend.py` (12: too soon is 429 with `Retry-After` and no SMS; after 61 seconds a new SMS and a token that logs in; the 60 seconds count from the newest code; the sixth code in an hour is 429 with "Try again in N minutes"; a new login counts too; the limit is per account and ends after an hour; bad, expired, tampered and access tokens are 401 and send nothing; an account that stopped being ready is refused; an SMS failure is 502 with no token; the old code still works until it expires; the per-address limit applies; nothing is logged), `tests/unit/test_rate_limit_retry_after.py` (5), `tests/unit/test_code_tokens.py` (the send time, which is our own claim `sent_at` and not `iat`, so a skewed clock cannot invalidate a token). **Backend: 1556 passed, `ruff` clean** (full run).
- **Frontend tests (written first):** `LoginForm.test.tsx` (37: the hint, the countdown in words and its end, "Send a new code" sends the token and never the password and uses the new token, the typed code is cleared, 429 "wait" counts those seconds, 429 "too many codes" keeps the button off, 401/403/502/500 sentences, "Start again" keeps the email and sends nothing, the buttons are at least 48 px and not red), `requestStaff.test.ts` (`Retry-After` read as whole seconds). **Frontend: 108 files, 1580 tests passed; `tsc` and `next lint` clean.**
- **Real browser** at 320, 360, 768 and 1024 px on the development server: `staff.spec.ts` login tests **12 of 12** (both steps fit the screen with targets of 48 px or more; with the browser's clock moved: 60 seconds counted, a new code sent with the token only, the password sent once, "Start again" back to the email).
- **A thing the browser test found:** the first version counted down with a chain of one-second timers, which cannot be fast-forwarded and is wrong in a background tab. The count is now a moment on the clock (`readyAt`), so it is right whenever the tab wakes.
- **Known limits:** the hourly count is kept in the API's memory (per instance, forgotten at a restart), so it limits cost, not attacks; an older code is not cancelled when a new one is sent (nothing is stored) and works until its 5 minutes end; a person who "starts again" can ask for a code at once, but that counts in the 5 an hour; the 403 sentence on the code screen is still the fixed "This account is deactivated." (the sentences for accounts waiting for approval come with the sign-up pages, Phase 3b).

- **Backend tests:** the new tests were written first and failed first (import errors, then the route list).
