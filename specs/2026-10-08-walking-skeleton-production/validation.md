# Walking skeleton in production: validation

How we know the feature is really done. What we build is in [requirements.md](requirements.md); the tasks are in
[plan.md](plan.md). Every test below proves NFR-05 or NFR-06. Tick a box only after the test exists and passes.

## How to run

- Backend tests: `docker compose exec backend pytest -q`
- Warnings as errors: `docker compose exec backend pytest -q -W error`
- Backend lint: `docker compose exec backend ruff check .`
- Frontend: `cd frontend && npm run lint && npm run typecheck && npm test && npm run build`
- Production checks: `curl -i https://<render-address>/health` and a browser on the Netlify address.

## Review-focus edge cases

- [ ] The API refuses to start with `APP_ENV=production` and a missing, default or short `JWT_SECRET` (already tested;
  confirm in the Render log that the real service started with a generated secret).
- [ ] `CORS_ORIGINS` has the exact Netlify address with `https://` and no trailing slash; a wrong value is the usual
  reason the browser blocks the API.
- [ ] The Render address in `NEXT_PUBLIC_API_URL` starts with `https://`, never `http://`.
- [ ] The first request after the API slept (about a minute) shows "not reachable" without crashing the home page, and
  the next request shows "connected". This is a known cost of the free plan (decision 3).
- [ ] The Blueprint takes the database address from the database, so no password is typed or committed.
- [ ] The API uses the database's internal address (same region, private network). Render says to use the internal
  address wherever possible; check in the Render dashboard that `DATABASE_URL` on the service is the internal one.
- [ ] `ipAllowList: []` really blocks outside connections to the database. The Blueprint spec only says that leaving it
  out allows every address, so confirm in the dashboard (database, Access Control) that no outside address is allowed.
- [ ] `alembic upgrade head` runs at start (see `backend/Dockerfile`) and works on an empty Render database.
- [ ] The production database holds no seed users, so there are no demo passwords online. If demo data is wanted
  there, decide that first; it is not part of this feature.

## Security checklist

- [ ] `git grep -n -i "secret\|password\|api_key" -- render.yaml netlify.toml` finds only variable names, never values.
- [ ] `JWT_SECRET` on Render was generated by Render (`generateValue: true`) or is 32+ bytes of random data, and is not
  the value in `.env.example`.
- [ ] Both sites answer on HTTPS only; `http://` redirects or fails (NFR-06). Render's load balancer ends TLS and Netlify
  serves HTTPS by default.
- [ ] No secrets in the commits; no `.env` change.
- [ ] `TRUSTED_PROXY_COUNT` is not `*`-like: it is the counted number from a real request, and the rate limit still
  separates two different clients (tested with two requests from two networks, or the unit tests plus one real check).
- [ ] Any temporary logging of `X-Forwarded-For` is removed before the commit and before the pull request (NFR-07).
- [ ] Render's free database is empty or holds demo data only.

## Smoke test

- [ ] `curl -i https://<render-address>/health` gives `200` and `{"status":"ok"}`.
- [ ] `https://<render-address>/docs` opens.
- [ ] `https://<netlify-address>/` opens over HTTPS and shows "API status: connected".
- [ ] A browser request from the Netlify page's origin to the API is not blocked by CORS (open the browser console on the
  Netlify page and run `fetch("<render-address>/health")`).
- [ ] After 15+ minutes idle, the first Netlify visit may say "not reachable"; reload shows "connected".
- [ ] A change pushed to `frontend/` ran only `Frontend CI`, and a change to `backend/` ran only `Backend CI`.
